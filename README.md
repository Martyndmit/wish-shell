# wish — проста командна оболонка Unix

Реалізація проєкту
[processes-shell](https://github.com/remzi-arpacidusseau/ostep-projects/blob/master/processes-shell/README.md)
з курсу OSTEP (*Operating Systems: Three Easy Pieces*) мовою C.
Використано лише стандартну бібліотеку C і системні виклики POSIX.

## Можливості

- **інтерактивний режим** (`./wish`) — друкує запрошення `wish> ` і виконує
  введені команди;
- **пакетний режим** (`./wish batch.txt`) — виконує команди з файлу, без
  запрошення;
- **запуск програм** через `fork()` + `execv()` + `waitpid()` з пошуком у
  *search path* (початково — `/bin`);
- **вбудовані команди** `exit`, `cd`, `path`;
- **перенаправлення виводу** `cmd > file` (у файл ідуть і stdout, і stderr);
- **паралельні команди** `cmd1 & cmd2 & cmd3`;
- єдине повідомлення про помилку `An error has occurred` у stderr.

## Збірка

Потрібні `make` і `gcc` або `clang` (Linux або macOS).

```sh
make            # збирає ./wish з -Wall -Wextra -Werror
make clean      # видаляє build/ і ./wish
```

Без `make`: `gcc -Wall -Werror -o wish src/*.c`

## Запуск

```sh
$ ./wish
wish> ls -la /tmp
wish> path /bin /usr/bin
wish> ls /tmp > out.txt
wish> echo one & echo two & sleep 1
wish> cd ..
wish> exit

$ ./wish batch.txt      # команди з файлу, по одній на рядок
```

## Тестування

```sh
make test         # офіційні тести OSTEP (22 тести)
make test-extra   # додаткові тести граничних випадків (23 тести)
```

`make test` запускає `scripts/run-tests.sh`. Тести OSTEP не скопійовані в цей
репозиторій: під час першого запуску скрипт клонує
[ostep-projects](https://github.com/remzi-arpacidusseau/ostep-projects) у
`.ostep-projects/` (папка в `.gitignore`), копіює туди `./wish` і запускає
`test-wish.sh`. Можна вказати вже наявну копію: `OSTEP_DIR=~/ostep-projects make test`.
Аргументи передаються тестеру: `./scripts/run-tests.sh -c` (не зупинятися
після першої помилки), `./scripts/run-tests.sh -t 7 -v` (лише тест 7, детально).

```
$ make test
test 1: passed
test 2: passed
...
test 22: passed
```

`tests/extra-tests.sh` перевіряє те, чого немає в офіційних тестах: табуляції,
CRLF, рядок без `\n` у кінці, рядок на 5000 аргументів, порядок пошуку в `path`,
відносні шляхи в `path` після `cd`, перезапис файлу через `>`, синтаксичну помилку
всередині паралельного рядка, вбудовані команди в паралельному рядку, поведінку
`exit`, запрошення в інтерактивному режимі тощо. Для кожного тесту перевірено,
що він падає на навмисно зламаній версії коду.

Додатково код перевірено під valgrind (без витоків пам'яті й помилок доступу),
з AddressSanitizer/UBSan, а також gcc 13 і clang 18 з
`-Wall -Wextra -Wpedantic -Wshadow -Wconversion` (Ubuntu 24.04).

## Структура проєкту

```
src/
  main.c       головний цикл: режими роботи, читання рядків (getline)
  parser.c/h   розбір рядка на команди: '&', '>', слова (strsep)
  executor.c/h виконання: fork/execv/waitpid, перенаправлення, паралельність
  builtins.c/h вбудовані команди exit, cd, path
  path.c/h     search path і пошук програми (access + stat)
  util.c/h     повідомлення про помилку, xmalloc/xrealloc/xstrdup
scripts/run-tests.sh   запуск офіційних тестів OSTEP
tests/extra-tests.sh   додаткові тести
Makefile
```

## Як це працює

### Головний цикл (`main.c`)

```
поки не exit:
    (інтерактивний режим) надрукувати "wish> "
    getline()                    -> EOF: exit(0)
    parse_line()                 -> синтаксична помилка: повідомлення, наступний рядок
    execute_cmdline()            -> запустити всі команди рядка і дочекатися їх
```

Без аргументів оболонка читає `stdin`, з одним аргументом — файл. Більше
одного аргументу або файл, який не вдається відкрити (чи це каталог), —
повідомлення про помилку й `exit(1)`.

### Розбір рядка (`parser.c`)

Рядок розбирається в три рівні, на кожному — `strsep()`:

1. за `&` — на окремі команди; порожні частини пропускаються, тому `&`,
   `cmd &` і `& cmd` коректні;
2. кожна команда — за першим `>` на частину з командою і частину з файлом;
3. кожна частина — за пробільними символами (`" \t\r\n\v\f"`) на слова.
   `strsep()` повертає порожній токен для кожної пари сусідніх роздільників,
   тому порожні токени пропускаються.

`strsep()` розрізає рядок на місці, тож слова в `argv` — це вказівники всередину
буфера рядка, без копіювання. Оператори не потребують пробілів: `ls>out`,
`p1.sh&p2.sh` працюють.

Результат — `struct cmdline` (масив `struct command`), де кожна команда має
`argv` (масив, що закінчується `NULL`, — саме такий потрібен `execv()`), `argc`
і `outfile` (файл після `>` або `NULL`).

Синтаксичні помилки (тоді відкидається **весь рядок**):

| Приклад              | Чому помилка                     |
|----------------------|----------------------------------|
| `ls >`               | немає файлу після `>`            |
| `> out`              | немає команди перед `>`          |
| `ls > a b`           | більше одного файлу              |
| `ls > a > b`         | більше одного `>`                |

### Пошук програми (`path.c`)

Оболонка не реалізує `ls` та інші програми — вона лише знаходить виконуваний
файл в одному з каталогів search path і запускає його. Для команди `ls` при
`path /bin /usr/bin` по черзі перевіряються `/bin/ls`, `/usr/bin/ls`; береться
перший, для якого `access(file, X_OK) == 0` і `stat()` показує звичайний файл
(`access(X_OK)` успішний і для каталогів, тому потрібна ще ця перевірка). Якщо
нічого не знайдено — помилка.

Команди завжди шукаються в path (як вимагає специфікація: з порожнім path
не запускається жодна програма). Відносні каталоги в path (`path tests`)
рахуються від поточного каталогу оболонки.

### Запуск програм (`executor.c`)

```
оболонка ── fork() ──> дочірній процес
   |                     [якщо є '>': open() + dup2() на дескриптори 1 і 2]
   |                     execv("/bin/ls", argv)  -- образ процесу замінюється на ls
   |                     (execv повернувся => помилка => _exit(1))
   |
   └── waitpid(pid) <─── дочірній процес завершився
```

**Паралельні команди.** `execute_cmdline()` працює у два проходи: спочатку
запускає всі команди рядка (не чекаючи), зберігаючи їхні `pid`, і лише потім
викликає `waitpid()` для кожного. Тому `p5.sh > f & p4.sh > f` виконуються
одночасно (це перевіряє тест 22), а керування повертається, коли завершилися всі.

**Перенаправлення.** У дочірньому процесі до `execv()` файл відкривається з
`O_WRONLY | O_CREAT | O_TRUNC` (створити або обрізати до нуля), і `dup2()`
ставить його на місце stdout (1) і stderr (2). Програма після `execv()` успадковує
ці дескриптори й пише у файл, нічого не знаючи про перенаправлення.

### Вбудовані команди (`builtins.c`)

Виконуються в самому процесі оболонки, без `fork()`: `cd` у дочірньому
процесі змінив би каталог лише дочірнього процесу. Команди зберігаються в
таблиці «назва → функція».

| Команда         | Поведінка                                                        |
|-----------------|------------------------------------------------------------------|
| `exit`          | завершує оболонку з кодом 0; з аргументами — помилка             |
| `cd DIR`        | `chdir(DIR)`; 0 або більше одного аргументу, невдалий `chdir` — помилка |
| `path [DIR]...` | замінює search path; без аргументів path порожній                |

## Важливі рішення

- **`_exit()` замість `exit()` у дочірньому процесі**, якщо `execv()` не вдався.
  Після `fork()` дочірній процес має копію буфера `FILE*` пакетного файлу, а
  зміщення у файлі спільне з батьківським процесом. `exit()` виконав би
  очищення stdio і відкотив би це спільне зміщення назад, до поточного рядка, —
  і батьківський процес виконав би частину команд **двічі**. Це перевірено
  експериментом і тестом у `tests/extra-tests.sh`.
- **Повідомлення про помилку через `write()`**, а не `printf()`: без буфера,
  тож воно з'являється відразу й не дублюється після `fork()`. Запрошення
  `wish> ` друкується `printf()` з негайним `fflush(stdout)` з тієї ж причини.
- **`path` зберігає копії** назв каталогів (`strdup`): аргументи вказують у
  буфер рядка, який наступний `getline()` перезапише.
- **`FD_CLOEXEC` для пакетного файлу**: програми, запущені оболонкою, не
  успадковують його дескриптор.
- **Синтаксична помилка відкидає весь рядок**, навіть якщо інші команди в ньому
  коректні. Помилки виконання (програму не знайдено, невдалий `cd`) стосуються
  лише своєї команди — решта команд рядка виконується.
- **Вбудовані команди в паралельному рядку** виконуються в оболонці в порядку
  появи: у `cd dir & ls` спершу виконується `cd`, тому `ls` запускається вже в `dir`.
- **`exit` у паралельному рядку** (`cmd & exit`) завершує оболонку лише після
  того, як виконаються й завершаться всі команди цього рядка.
- **`>` для вбудованих команд** специфікація не визначає. Тут вони
  поводяться як інші команди: файл створюється, а повідомлення про помилку
  потрапляє у файл. Оскільки вбудована команда виконується в самій оболонці,
  її stdout/stderr тимчасово перенаправляються (`dup()` зберігає оригінальні
  дескриптори, `dup2()` перенаправляє і потім відновлює).

## Історія розробки

Кожен етап — окремий коміт, після кожного проєкт збирається й працює
(`git log --reverse`):

1. система збірки й базовий цикл REPL (`getline`, вихід за EOF);
2. пакетний режим і повідомлення про помилку;
3. запуск програм: розбір на слова, search path, `fork`/`execv`/`waitpid`;
4. вбудовані команди `exit`, `cd`, `path`;
5. перенаправлення `>`;
6. паралельні команди `&` — після цього етапу проходять усі 22 тести OSTEP;
7. `make test` для офіційних тестів;
8. додаткові тести граничних випадків (`make test-extra`);
9. виправлення: каталог як пакетний файл тепер вважається помилкою;
10. документація.

## Обмеження

Як і передбачено завданням, `wish` не підтримує лапки й екранування,
змінні середовища, конвеєри `|`, перенаправлення вводу `<` і дописування `>>`,
запуск програм за абсолютним чи відносним шляхом без path (`/bin/ls`, `./prog`;
можна зробити `path .`), історію команд і обробку сигналів (Ctrl+C завершує
й оболонку).
